# Interior engine — SP04

Status: implementation candidate; not a visual acceptance or production release. The canonical Russian product specification remains authoritative. Five original schematic vector scenes are included; their artistic fidelity is not approved. No third-party image, user photo, external SVG or downloaded model is embedded.

## Ownership and contracts

`decor/catalog.py` is the server-authoritative registry. Scene schema 1 contains background, lighting, mandatory surface, mandatory device skin and up to sixteen optional objects. The room core's legacy `interior` selects the fallback for an unpublished location. Once published, each of `lounge` and `table` has an independent revision and scene copy. Later Room Core interior edits affect only unpublished locations; use the scene editor to reset a published location. The catalogue has five immutable presets (apartment, garage, beach, kindergarten boat, card club). All provide at least two compatible surfaces; table, mat and deck semantics are distinct. There are three lighting options, three stereo skins, chair variants and individually placed S-50 speakers. No cafe or dacha. The two-layer Vega depiction has one cassette deck and one amplifier; no CD/vinyl third tier. The beach is an illustrative river landscape, not a verified historical photograph; the kindergarten boat is a stylized metal playground structure. Model-specific visual review remains required. `SceneCanvas` renders trusted primitives by asset ID. Scene editor provides a pointer-controlled draft and keyboard/touch range inputs. Local draft history is bounded to 30 steps, with one undo step per drag gesture. The scene has an explicit semantic play surface and device: they cannot be removed; optional decorative objects draw below these functional slots. Roster is rendered separately by the SP03 layout engine over the scene and is not part of its persisted geometry. Observer rail remains separate. At narrow viewports player readability takes priority over exact scene scale.

## Shared decoration and templates

Only active room members can read. Owner or delegated designer may publish, using both current Room Core version and the independent scene revision. Pydantic rejects unknown assets, arbitrary URLs/HTML, incompatible surfaces, duplicate IDs, excessive counts, and out-of-range positions, scales, rotation or layers. Transactions use the RoomService receipt/audit mechanism. A stale version returns 409, retains the local draft, and prompts a reload; never overwrite silently. Draft actions perform no provider calls. A successful commit fences the existing room hub; viewers fetch a fresh projection once per revision notification (additional core refresh is possible). The server is authoritative, not local component state. A failed fetch can be retried manually. No periodic scene polling.

Per-UID private reusable library supports up to 12 saved templates. Copy to a draft in another room where the user is designer; save new or update/delete with expected template revision. A published scene is a value copy, not a mutable pointer; deleting a template never removes a published scene. The library is scoped to creator UID, not room ownership. There is no arbitrary resource upload or template marketplace. Full RoomTemplate bundles (roles/capacity/activity/media presets combined) remain deferred until game host contracts settle; these are InteriorTemplates only. Scene preference hide/contrast/zoom is local to the current mounted room, not written to Firestore. Persistence of personal preferences across reloads is a follow-up, not claimed here.

## Acceptance and future integration

SP05/06 must bind activity surfaces and immutable logical seats, and defer unsafe scene changes while an activity is running. No game state exists in SP04. Validate mobile pointer and keyboard editor, conflicts across two browsers, asset bounds and historical visual accuracy before release. Source artwork is intentionally schematic.
