## 1. Цель, границы и приоритет документов

Создать удобный закрытый онлайн-стол для трёх друзей, напоминающий совместную игру дома: собственная рука снизу, соперники по сторонам, общий прикуп, взятки, тетрадная пулька, ретро-магнитофон, видеосвязь. Играть по ранее утверждённым запорожским домашним правилам, непрерывно по 4–6 часов дважды в месяц, без дополнительных платных услуг. Интерфейс игры и пользовательские документы — на русском; публичная карточка портфолио — на английском. Названия технических файлов английские, русскоязычные исходники и документы соблюдают политику `*.ru.*`.

Это модернизация существующей реализации, а не новый продукт или второй движок. Сохраняются маршруты, публичная карточка, идентичность проекта, сохранённые партии, исходный учёт очков, существующие гранты и общая архитектура сайта. Объём: Realtime, новый стол, взаимодействия, общее пространство, эксплуатация/полнота сценариев. Не входят: боты, четыре игрока, ставки на деньги, публичные комнаты для гостей, 3D-движок, платный TURN, платная инфраструктура, облачная запись, неподтверждённые права на музыку, изменение домашних правил по собственной инициативе.

### 3.1. Дополнительные согласованные требования

- В центре — прикуп и свободное поле для карт текущей взятки; сброс при сносе визуально отдельно и доступен только уполномоченной руке.
- Мои карты по центру внизу; слева и справа — руки соперников, обычно рубашкой вверх. Аватары или добровольное видео у соответствующих игроков; при отсутствии аватара — нейтральная пиктограмма. Присутствие отдельно от доступности медиа.
- Левое меню: правила, пулька, история/рейтинг, звук/музыка, видео/запись, личные настройки, перерыв и выход/возврат в лобби.
- После взятия прикупа убрать его с основного поля; доступен общий повторный показ только ранее законно открытых карт. Не открывать закрытый прикуп.
- Горизонтальная панель ставок над рукой: `ПАС | 6 | 7 | 8 | 9 | 10 | МИЗЕР`; первый клик по числу раскрывает `♠ | ♣ | ♦ | ♥ | БК`, второй отправляет ставку; «Здесь [ставка]» — только при серверном разрешении. Отдельная стадия окончательного заказа. Специальные варианты без прикупа доступны, когда разрешены.
- Общий магнитофон справа внизу; при клике увеличивается без перекрытия всей игровой области. Синхронные команды, локальная громкость. При закрытии музыка не обязана останавливаться.
- Трёхсторонняя общая видимость действий; инициатор каждого общего запроса назван. Игровой авторитет всегда серверный, клиент лишь отображает.

### 4.1. Квоты, проверенные 24.11.2026

Firestore Standard free quota: 50 000 reads, 20 000 writes, 20 000 deletes в сутки, 1 GiB хранения для одной бесплатной БД проекта; TTL delete не бесплатен и требует billing. Render: 750 free instance hours в месяц на workspace, спящие сервисы и перезапуски возможны, входящие WS-сообщения поддерживают активность, но не гарантируют доступность. Vercel Hobby — некоммерческое использование и действующие квоты. Новая поддержка WebSocket на Vercel стала общедоступна (changelog октября 2026), но соединения учитываются по правилам Functions; длительность и стоимость нельзя предполагать неограниченными. Здесь игровой WS предлагается на уже существующем Render, а не на новой Vercel Function, чтобы не держать параллельный дорогостоящий транспорт. До начала PR10 подтвердить фактический тариф и конфигурацию, не менять их автоматически.

Официальные источники: [Firestore quotas](https://firebase.google.com/docs/firestore/quotas), [Firestore pricing](https://firebase.google.com/docs/firestore/pricing), [Firebase pricing plans](https://firebase.google.com/docs/projects/billing/firebase-pricing-plans), [Render free](https://render.com/docs/free), [Render WebSockets](https://render.com/docs/websocket), [Render incoming WS changelog](https://render.com/changelog/free-web-services-now-remain-active-while-receiving-websocket-messages), [Vercel Hobby](https://vercel.com/docs/plans/hobby), [Vercel WS GA](https://vercel.com/changelog/websocket-support-is-now-generally-available). Тарифы меняются, перепроверить перед релизом. Квота Firestore делится с сайтом; дневной лимит нельзя усреднять по месяцу. Биллинг не подключать даже ради TTL, relay или расширенных метрик.

### 4.2. Контрольные оценки нагрузки (не измерения)

Пусть `P=3`, `T=21600` секунд (6 ч), `i` — период, `d` — число чтений за запрос. `requests=P*T/i`; `reads=requests*d`; при heartbeat каждые 45 с и 4 writes/мутацию `writes=3*21600/45*4=5760`. Существующие 8 с дают 8100 запросов, даже неизменившаяся версия требует чтения; 2 с — 32400 запросов. Медиа polling 6 с × 2 docs ≈ 21600 reads; при 2,5 с ≈ 51840 reads. Это нижние оценки, не включают grants/SDK retry.

Проектная модель: при `D` раздачах, `A` средних изменяющих командах на раздачу, `R` реальных чтениях и `W` реальных записях на принятую команду: `reads_total=D*A*R+reads_auth+reads_recovery+reads_media+reads_history+reads_cleanup+reads_retry`; аналогично для writes. Пример для планирования: 40 раздач × 44 команды = 1760 команд, при 4 writes ≈ 7040, до остальных расходов. 60×45×4=10800, уже больше цели; поэтому нельзя обещать 10k при любой скорости игры, нельзя маскировать превышение отказом от надёжной записи. Не считать уведомление WS, анимацию, heartbeat или управление громкостью игровой мутацией. Для резерва 8 ч считать и фактические максимумы, и общесуточные показатели.

Не выдавать оценку за точное глобальное потребление.

История/рейтинг загружаются по запросу пользователя, не при каждом обновлении стола. Графики строятся из уже полученных данных.

## 5. Архитектура доставки и изоляция (PR10)

```text
Browser (Next.js protected page)
  |-- same-origin HTTP /api/preferans/* --> Next BFF --> FastAPI
  |-- authenticated WSS (configured Render origin) --> Preferans realtime adapter
  |                                                    |
  +-- two P2P WebRTC peers (only optional media)         +-- service / store / domain
                                                         +-- Firestore durable state
```

HTTP мутации по существующему маршруту остаются основным совместимым API. WS доставляет версию/персонализированный снимок после commit, присутствие, общие presentation-события и в дальнейшем адресные SDP/ICE. Не отправлять через WS целиком `GameState`, сырой event log, токены, чужие руки, закрытый снос, UID или скрытый прикуп. Не создавать глобальный backend registry, общий кэш чужих проектов, отдельное приложение, внешнюю БД, Redis/relay/таймерный сервис за деньги. Папки проекта остаются изолированными; хосту разрешены только тонкие adapters/config/registration, существующие зависимости и минимальные изменения auth routing. Не менять Fleet, Workforce, chat/RAG, публичные страницы, общую авторизацию без конкретной доказанной необходимости.

### 5.1. Выбор транспортного решения и согласование с хостом

Прямой WSS к Render — узкое исключение из текущего правила root `AGENTS.md` «use /api/*, do not call backend host directly». Прежде чем кодировать, PR10 оформляет краткое ADR (в `docs/` проекта, при необходимости одна ссылка из host architecture) с конкретной угроз-моделью, конфигурацией и доказательством совместимости; это не разрешение на произвольные прямые REST-запросы. В браузере не зашивать `onrender.com`; получать разрешённый `wss:` origin из доверенной серверной конфигурации BFF, валидировать путь/протокол/allowlist. Для dev — явно разрешённый localhost `ws:`. Не использовать Vercel Functions как шестичасовой WS relay без отдельной проверки лимитов, стоимости и авторизации. Если исключение не соответствует требованиям хоста или SDK, остановить соответствующий кусок и предложить альтернативу с измерением, а не расширять доступ.

**Проектный контракт bootstrap:** `POST /api/preferans/rooms/{id}/realtime-ticket` через BFF, owner/project/room permission, same-origin guard; backend выдаёт короткоживущий одноразовый opaque ticket (целевой срок ≤ 60 с), привязанный к комнате, месту, пользователю/актуальному гранту и типу соединения. Предпочтительно сервер хранит ограниченную таблицу ticket в процессе, без новых Firestore writes; restart инвалидирует ticket, клиент получает новый. WS handshake проверяет Origin, лимиты и протокол, первая frame — ticket (не URL, не query, не localStorage, не логи); таймаут авторизации до 5 с, до неё не выдавать ни одного room payload. Атомарно погасить ticket, replay и просрочка отклоняются. Не передавать Firebase service credentials или session cookie через URL; не расширять CORS ради подключения. Проверять авторитетный grant при выдаче, подключении и с ограниченным сроком кэша; целевой интервал перепроверки ≤ 60 с, отзыв и expiry приводят к закрытию и очистке view. Если перепроверка недоступна — закрыть, не продолжать доступ бесконечно. В каждой значимой HTTP мутации существующая серверная авторизация сохраняется. `View` не получает игровые WS payload или право мутаций; Owner вне стола не видит скрытое игровое/медиа-состояние. Не доверять seat из входной frame. На новую вкладку того же игрока — контролируемое замещение активной управляющей сессии либо режим без команд, не два места.

### 5.2. Протокол (предлагаемые названия, точная схема ADR PR10)

| Событие | Направление | Смысл |
|---|---|---|
| `authenticate`, `ready`, `auth_expired` | C→S / S→C | Одноразовый bootstrap, версия протокола, закрытие при потере доступа. |
| `snapshot` | S→C | Seat-specific projection, `room_id`, `game_version`, `deal_id`, `presentation_version`, `server_now_ms`, контролируемый epoch/sequence. |
| `room_updated` | S→C | Только после durable commit; по возможности вложить уже вычисленную разрешённую проекцию, чтобы не вызывать три HTTP reads. |
| `ping/pong` | оба | Heartbeat ~15–20 с, presence в памяти, без каждой записи в Firestore. |
| `presence_changed` | S→C | Публичное состояние места и время последнего подтверждения, без идентификаторов Firebase. |
| `presentation_changed` | S→C | Разрешённое общее состояние интерфейса, отдельная версия. |
| `media_signal` / `consent_changed` | оба | В PR13: адресный ограниченный relay/запись согласий; никогда не broadcast SDP/ICE. |
| `resync_required` / `error` | S→C | Разрыв последовательности, безопасная перезагрузка view, понятная ошибка; без стеков, payload/секретов. |

Валидировать схемы, версию протокола, длины, предел очередей, частоту команд, размер frames, таймауты и backpressure. Не допускать неограниченных pending/clients/tasks; медленный клиент отключается и resync. Для значимых действий существующие expected_version/idempotency_key остаются; повтор с тем же ключом не начисляет второй штраф или медаль. Порядок доставки не равно порядку commit; клиент отбрасывает устаревшие версии, при пропуске получает полный актуальный seat view. После disconnect exponential backoff с jitter (например 1,2,4,8,15,30 с с верхней границей); HTTP fallback ограничен и не запускается параллельно непрерывному здоровому WS. Возврат к WS прекращает резервный цикл. Никакой новой 2-секундной бесконечной нагрузки.

### 5.3. Авторитет состояния, restart, масштабирование

Firestore хранит durable room/game/private state, game version, результаты, права и журнал; нельзя заменить его памятью Render. Кэш/connection hub и ephemeral UI события — только ускорение. Broadcast вызывается после успешного завершения транзакции, не из callback транзакции, которую SDK может повторить. Для трёх мест сформировать отдельные проекции через общий `seat_view` из уже подтверждённого состояния (или единичный авторитетный read при отсутствии безопасного результата) и доставить только соответствующему соединению; не раздавать скрытые карты публичному каналу. При конфликте HTTP/WS подтверждённая версия побеждает, UI блокирует двойной клик на in-flight действие, без speculative score. При restart/rolling deploy все клиенты восстанавливают snapshot, не генерируют новый game ID. Проверить фактический worker/instance count FastAPI: in-memory hub корректен только при одном процессе/инстансе для данной комнаты. Если хост многопроцессный, нельзя менять глобальный worker count без оценки влияния на сайт; предусмотреть безопасный механизм сверки/доставки (например ограниченный серверный watcher или fallback) и ADR с измерением. Отсутствие доставки не означает потерю commit. Не добавлять платный broker. Все серверные фоновые задачи ограничены lifecycle и завершаются при shutdown.

## 6. Присутствие, состояние комнаты, паузы и время

### 6.1. Присутствие

- Локальное здоровье канала не равно состоянию остальных. На каждом аватаре статус подтверждается сервером: зелёная точка «В игре» при актуальном heartbeat; жёлтая «Переподключение» до 60 секунд с момента обнаружения потери; красная «Отключён» после 60 секунд. Проектный default — обнаружение потери при закрытии WS или пропуске ожидаемых heartbeat (порог порядка 25–40 с, точное значение по замерам), не обещать мгновенного обнаружения физического разрыва. Для fallback требуется доказуемое присутствие всех троих через редкий авторизованный запрос; не считать online одного клиента доказательством остальных.
- Камера/микрофон могут быть отключены, статус игры остаётся зелёным. Очередь хода — золотистый ободок и доступный текст, а не тот же индикатор связи. Для светлой игры отличать владельца руки и реально управляющего игрока (`turn`/`controller`).
- На disconnect одного участника игровая пауза включается при обнаружении; при возвращении всех восстанавливается без приглашения, но не сбрасывает иные причины паузы. Старый `pulse` сохранять только как совместимый ограниченный fallback на период rollout; в нормальном WS режиме heartbeat не пишет события игрового журнала и не увеличивает game_version. Нужное durable checkpoint для активных таймеров делать редко/при переходах, не каждые 15 с для всей комнаты.

### 6.2. Независимые причины паузы

Не один boolean. На сервере вычисляется множество `pause_reasons` (предлагаемые enum): `connection_lost`, `shared_overlay`, `break`, `undo_vote`, `storage_unavailable`, `recovery` и имеющиеся доменные блокировки. `playing_allowed = phase_allows_action && no_blocking_pause`. Не допускать, чтобы закрытие одного объекта очищало все причины. Представление и presence не должны менять математику игры; durable pause/timer transitions всё же должны быть атомарно сохранены, если влияют на законность ходов. Отдельная `presentation_version` не увеличивает game version на каждый клик, но действие проверяет обе версии/актуальные причины паузы. Согласовать структуру данных и атомарность в ADR; допустима запись при реальном открытии/закрытии влияющего на таймер объекта, но не каждый кадр или playhead музыки.

| Причина | Допустимые действия | Как возобновить |
|---|---|---|
| Нет причин | Обычные серверные легальные команды | — |
| Пулька или магнитофон | Просмотр/управление/закрытие; игровые ходы блокированы | Закрывает любой участник; только эта причина снимается |
| Последняя взятка | Просмотр/закрытие; следующий допустимый игровой ход — специальное исключение UX-11 | Одна атомарная команда закрывает overlay и делает ход; другие причины паузы всё равно запрещают ход |
| Повтор прикупа | Предлагаем применять ту же общую паузу, что для пульки; можно закрыть любому | Снять причину после закрытия; только законно ранее открытые карты |
| Общий перерыв | Управление готовностью, необязательные функции | Три явных подтверждения в текущем break ID; disconnect аннулирует актуальную готовность отсутствующего до reconnect |
| Потеря связи / восстановление | Reconnect, read-only, безопасные управляющие действия | После подтверждения всех троих и восстановления актуального состояния |
| Голосование | Ответы на запрос, не обычный ход | Существующие правила голосования, согласие/отказ/таймаут |
| Хранилище недоступно | Только безопасное чтение имеющегося snapshot и reconnect; не подтверждать новые ходы | Авторитетное восстановление, reconciliation |

Для последней взятки «следующий ход» означает легальную команду хода текущей руки, не любой клик, локальную сортировку или настройку. Если иной вид допустимого действия нужен после последней взятки (settle/сдача), не допускать тупика: объект можно закрыть явно. При попытке открыть другой общий объект сервер сериализует действие; инженерный default — заменить текущий объект новым атомарно без промежуточного возобновления. Одновременные запросы через expected presentation version; устаревший получает resync. Каждый видит инициатора. При остановке сервера/переключении вкладок не продолжать игру автоматически, если причины ещё не восстановлены. В PR10 определить общий pause API, PR13 подключить панели.

### 6.3. Серверные таймеры

Хранить состояние таймера, `remaining_ms`, `deadline_ms` (только при active), actor/decision ID, cost snapshot, count начисленных штрафов, `pause_reasons` и опорное серверное время. Формула freeze: `remaining=max(0,deadline-now)` в атомарном переходе из active при первой причине; дальнейшие причины не уменьшают остаток. Resume: только когда нет причин, `deadline=now+remaining`. Для истечения: ровно один штраф за interval ID, `3 × C_ref` по действующему ruleset; новый интервал только пока тот же игрок обязан действовать. Пауза при наступлении дедлайна и команда на границе — детерминированный серверный порядок с тестом гонки; не начислять штраф за неизвестный офлайн-период. При аварийном restart без точного времени потери связи консервативно восстановить остаток последнего доверенного checkpoint (может дать лишнее время, но не несправедливый штраф), затем возобновить при всех подключённых. Не переносить старый счётчик на другую руку. Клиент только показывает рассчитанное время; коррекция clock skew по `server_now_ms`.

Все игровые отсчёты, в том числе 5 с до сдачи, замораживаются. Для голосования об отмене существует собственный 120-секундный дедлайн: он не может быть заморожен своей же причиной `undo_vote`, иначе не завершится; при внешнем перерыве/отсутствии замораживается согласно UX-10/14, после — оставшееся время. Транспортный heartbeat, ticket expiry, auth revocation, consent safety и технические timeouts не являются игровыми таймерами и не замораживаются. Это инженерная детализация; сохранить прежние правила двух голосов, повторного запроса и недопустимости отмены после последующей заявки/хода. Не создавать зависимостей, требующих одновременно закрытого окна и недоступной кнопки.

### 6.4. Автоматическая следующая сдача

Первый старт — явный, администратор после заполнения трёх мест и согласия всех на правила/пулю/сдающего (по исходному ТЗ). Последующие — ровно одна через 5 с после полного завершения расчёта текущей сдачи, выбора направления очков/помощи и остальных обязательных решений; закрытая/архивная партия не запускается снова. Публичный countdown виден всем. Серверное `deal_id` и durable transition с идемпотентным ключом на следующую раздачу, не три клиентских `setTimeout`. При паузе сохранить остаток; при рестарте восстановить безопасно. Проверить гонку ручного старта старым клиентом, двойной timeout, два запроса, закрытие последней пули, passout bonus двум игрокам. Не пропускать итоговую демонстрацию и не раздавать до settlement. Исторические правила ротации и первого сдающего сохраняются.

## 7. Пространственный игровой стол (PR11)

### 7.1. Макет и навигация

Цель — 2D-стол с тёплым домашним интерьером, не копия присланных скриншотов. Вход в комнату заменяет длинную страницу с карточками полноценной сценой; в лобби — явное создание/выбор комнаты, заполнение мест, доступность приглашения и крупная кнопка старта рядом с готовностью (без прокрутки под стол). Общий navbar сайта сохраняется; внутри проекта адаптивная полноэкранная/компактная игровая область, без изменения глобальных CSS. Для компактного режима меню может быть узкой полосой и flyout; в активной игре важная информация без вертикальной прокрутки. Без 3D, стороннего canvas-движка и обязательного fullscreen. Перед PR11 сделать локальный интерактивный прототип с фиктивными состояниями аукциона, игры и открытых рук; Owner принимает пространственное расположение до интеграции с реальными действиями. Прототип не публикуется как доступ к игре и не требует отдельного PR.

```text
┌──────┬────────────────────────────────────────────────────────────┐
│ меню │     аватар/видео L        прикуп        аватар/видео R    │
│      │     рубашки L          (две карты)       рубашки R         │
│прав. │        пулька         поле розыгрыша                       │
│истор.│                L-карта   R-карта                           │
│рейти.│                     моя карта                             │
│медиа │           контекстная панель торгов / решений             │
│настр.│       моя рука: сгруппированные классические карты       │
│пауза │                  мой аватар / статус         магнитофон   │
└──────┴────────────────────────────────────────────────────────────┘
```

Пулька возле центра, не на месте розыгрыша; повтор взятки и прикупа рядом со своими объектами. Показ контракта/роли/взяток/сдающего ненавязчивый и в соответствующем месте; крупные панели «Ожидание хода», «Правила», «Подключение», «История и рейтинг» убрать со стола, перенести в меню или контекстную подсказку. Не полагаться на цвет без доступной подписи. Для desktop проверить 1280×720, 1440×900, 1920×1080; для landscape смартфона реальные viewports примерно 667×375, 844×390, 915×412 с safe-area, браузерной панелью, zoom. Portrait: предложение повернуть экран; не требовать browser orientation lock, который не везде поддерживается. Не блокировать reconnect, выход и отозвать согласие на запись из-за portrait. Не создавать горизонтальный скролл всего сайта. Карты и главное действие доступны без точного drag; keyboard/touch, focus, screen reader, reduced motion, читаемый контраст, минимум визуального шума. Не рассчитывать размеры только по 100vh; safe area и динамические viewport units.

### 7.2. Места и вращение

Server seat indices `0,1,2` сохраняются. У игрока `s`: `bottom=s`, `left=(s+1)%3`, `right=(s+2)%3` (согласованная ротация по часовой стрелке). Проверочные примеры: 1→слева 2 справа 3; 2→3/1; 3→1/2. Один чистый mapping для аватаров, карты взятки, открытых рук, пульки, камер, аудио, меток сдающего. Не сортировать соперников просто по числу места. Не преобразовывать game command seat из визуальной стороны без inverse map. Визуальные тесты для всех трёх перспектив и каждого сочетания turn/controller; никакой перестановки фактической очередности торгов/ходов.

### 7.3. Карты и ассеты

32 уникальные карты: 7–Т, четыре масти, русские В/Д/К/Т. Изображения оригинальные либо с доказуемой лицензией (например public domain/разрешённое воспроизведение); классический внешний вид русской атласной колоды без копирования неизвестных современных сканов, брендов или чужого интерфейса. Записать provenance/лицензию ассетов и их размер в `docs/ASSET_LICENSES.ru.md` на этапе реализации; пока ассеты не созданы. Векторные SVG или оптимизированный локальный atlas, отдельная безопасная красноватая рубашка с перекрёстным полосатым узором. У чужих закрытых карт DOM содержит только одинаковые backs и публичное число, никакого card ID, скрытого alt/data attr, CSS preload по фактическим рангу/масти или отладочного store. Разрешённые открытые руки — точно из серверного view. На 10 и 12 картах rank+suit читаются, группа масти имеет зазор. Лицевые карты с традиционными фигурами В/Д/К, стандартными мастями/угловыми индексами. Поддержать доступные названия рангов и мастей, не менять доменные enum. CSS Modules, локальные ассеты, запрет лишних глобальных правил, без передачи личных фото в Git.

### 7.4. Аватары и видео

На месте каждого виден разрешённый display name из существующего профиля, аватар/нейтральный fallback, индикатор присутствия, ободок хода, число взяток/карт и заявка. Не раскрывать email/UID/служебный токен; использовать безопасную профильную проекцию, не читать произвольные профили по переданному UID. Камера в той же зоне, когда разрешена; видео может быть скрыто локально, игра не блокируется. Во время выбора светлой игры показать реальную открываемую руку и кто ей управляет, отдельный контур выделения. Не смешивать player turn и card owner.

## 8. Игровые действия (PR12)

### 8.1. Торговля и окончательный контракт

Панель над собственной рукой появляется только в нужной фазе. `ПАС | 6 | 7 | 8 | 9 | 10 | МИЗЕР` — порядок кнопок, не ранг. Число раскрывает ряд `♠ ♣ ♦ ♥ БК` рядом, второй клик сразу отправляет серверу заявку, без подтверждения. `Мизер` и `Мизер БП`, `10 БП` с пятью разрешёнными вариантами, отображаются через явное подменю согласно legal_bids; не смешивать два разных контракта с одинаковым текстом. «Здесь 7♣» появляется только первой руке, когда `can_say_here=true`, никогда для 6♠. Показывать публичную последнюю заявку возле аватара и её удержание/пас. Никакой доступности команды, вычисленной исключительно по клиентскому рангу. При ошибке `version conflict` — показать актуальные действия, не повторять автоматически другую заявку. После победы в торговле — прикуп/снос, затем отдельная панель «Назначить игру» (минимум по выигранной заявке, мизер не добавляется в обычный заказ); специальный БП не раскрывает скрытый прикуп. Сохранить договорённые особенности «Обязаловки», паса, полвиста, светлой/тёмной защиты и исключения по контрактам. Серверные `legal_contracts`, `legal_cards`, текущий controller — источники истины. Русские шуточные тексты отмены ставки и карты из исходного ТЗ сохранить; 120 с, оба соперника должны согласиться, отмена только пока не было последующего действия.

### 8.2. Прикуп, ход и анимации

Прикуп до раскрытия: ровно две рубашки (не подставлять закрытые значения). Обычный прикуп показывается всем при разрешённом раскрытии; после взятия убрать и дать кнопку «Показать прикуп». На распасах открывать первую и вторую карты по правилам перед соответствующими взятками; повтор может показать только открывшуюся часть, не вторую заранее. На играх БП кнопка отсутствует/неактивна; ни одна карта прикупа не попадает в общие DTO. Снос — две закрытые карты, отдельная зона, игрок видит выделение, соперники только факт и допустимое число; не повторять снос при показе прикупа. Если выигрышный контракт или мизер БП меняет права доступа, пересоздать view сервером.

Текущая взятка — три слота относительно владельца сыгранной карты; карта появляется после подтверждения сервера. Поддержать click/touch/drag с альтернативой без drag; не менять существующее правило подтверждения хода карты без решения Owner (двухкликовая ставка не означает мгновенный ход картой). В фазе сноса click/drag только выбирает две карты, подтверждение отдельно. На ходах подсветить legal_cards, не сообщать сопернику подсказки о закрытой руке. Завершённая взятка должна остаться визуально различимой короткое время, затем уходить к победителю; server next turn не задерживается анимацией. Если клиент догоняет несколько версий/reconnect — показать итоговый snapshot без проигрывания всех старых анимаций. При reduced motion отключить эффекты без потери состояния. Анимация сдачи: выдача по две с прикупом после первого круга, 10 каждому и 2 в прикуп; использовать только публичное число карт и собственную разрешённую руку. Звук локален и выключаем; ограниченная длительность эффектов; никаких повторных транзакций для кадров анимации.

### 8.3. Сортировка и настройки

Сортировка по умолчанию: сначала масть с максимальным числом карт, затем старшая карта масти по убыванию, равенство разрешается стабильным `♠,♣,♦,♥`; внутри группы Т,К,Д,В,10,9,8,7. Разрыв между группами. Режим фиксированного порядка/ручной, перетаскивание мышью/пальцем и клавиатурная альтернатива; после изменения руки удалять сыгранные карты, добавлять новые детерминированно; не сбрасывать ручной порядок при каждом snapshot. Сохранять предпочтения по UID через существующий безопасный механизм проекта, между партиями и устройствами, кэш локально; запись только при реальном изменении настройки, не на каждое перемещение. Личная раскладка текущей сдачи не видна остальным, не влияет на версию партии. Локальная громкость, размер, reduced motion, вывод видео, музыка mute — персональные, не общий presentation event.

### 8.4. Стадии и целостность

Оставить все серверные стадии: lobby, auction, discard, declare, defense first/second/reconsider, choose_mode, opening_lead, play, settlement, between, closed/archived; названия адаптировать к существующей enum, не придумывать дубли. Перемещение панели не удаляет права «без трёх», предложение исхода мизера, отмену карты/ставки, счётчик, корректировки. Перепроверить тестами 6♠, мизер БП, тотус БП, распасы, светлую игру, распределение помощи, последние очки, double gold, triple draw. Запрещённые действия не должны работать через ручной API вызов. Неполные workflows из §13 не маскировать интерфейсом.

## 9. Общее пространство и пулька (PR13)

### 9.1. RoomPresentation и синхронизация

Публичное состояние для трёх игроков: `overlay_type` (`none`, `score_sheet`, `radio`, `last_trick`, `widow_replay`), `overlay_id`, `initiator_seat`, `opened_at`, `presentation_version`, ссылка на разрешённый публичный snapshot/версию сдачи, `music_state`, `break_id/ready_seats`. Формы и названия проектные, не новый источник игровой правды. Только сидящие игроки открывают/закрывают; read-only и посторонний не участвуют. Взаимное исключение overlay действует глобально; local mute/minimize не снимает серверную паузу; закрытие по клику на стол вне увеличенного объекта — общая команда, для last_trick применить UX-11. Переподключение показывает актуальный открытый объект и актуальную паузу. Старый overlay при смене deal ID закрывается, не раскрывает устаревшие данные новой сдачи. Для общих панелей хранить только метаданные/публичные данные; влияющие на паузу переходы должны быть надёжными, музыкальный playhead можно восстанавливать из команды и времени без постоянной записи. Если эпhemerals потерялись при restart, безопасно закрыть или восстановить по durable записи, но не возобновлять при иных причинах.

Последняя взятка: показать ровно предыдущие три законно сыгранные карты текущей сдачи, их владельцев, ведущую масть и победителя, текст «[имя] попросил показать последнюю взятку». До первой завершённой — недоступна. Не предоставлять свободный просмотр чужих исторических рук. Повтор прикупа: см. §8.2. Открытие пульки/магнитофона/взятки при уже действующем счётчике останавливает его, закрытие восстанавливает остаток только если нет других причин. Общие события не должны менять счёт или случайно разрешать команду другого игрока.

### 9.2. Классический лист пульки

Малый листок в клетку на столе, при клике увеличивается как тетрадный лист. Три зоны с общей целью пули в центре, треугольные границы, полоса горы, пули, два направления вистов на соперников; ручной стиль цифр, аккуратные зачёркивания/следующая запись по исторической модели, красный акцент исправлений. Каждый видит свой сектор снизу (тот же mapping §7.2), направления вистов не меняются при повороте. Показывать суммы и последовательность записей на основе серверного ledger; не выдумывать рукописные прошлые записи, если доступны только итоги. Если нужен подробный журнал — lazy page, не грузить все события каждую секунду. Для accessibility — табличная альтернатива, те же данные и одна арифметика. Лист можно открыть любому, у администратора отдельный режим корректировки активной партии с preview, обязательной причиной, журналом до/после; завершённые immutable results не изменяются. Лист не является редактором новых формул. Ошибки и корректировки не перезаписывают историю. После финала показывать результат, места, направленные условные наказания и их выбранный вариант из исходного ТЗ; никакого финансового расчёта в реальных деньгах.

### 9.3. Меню, история и рейтинг

Левый компактный sidebar: правила/FAQ, пулька, история, рейтинг, звук и музыка, видео/запись, личные настройки, общий перерыв, вернуться в лобби. Обычные личные панели не становятся общей паузой, пока не открывают один из синхронных объектов. История и рейтинг загружаются при открытии; read-only history/ranking по grants, а не по наличию места. Сортировка по всем столбцам, по умолчанию золотые медали; график трёх игроков реагирует на выбранную числовую метрику, хронология неизменна; два столбца полученных/нанесённых голых ударов. Сохранить immutable историю PR7, не пересчитывать прошлые результаты без утверждения миграции. Прозрачный lobby: список доступных комнат для пользователей с правом играть, свободные места, состояние, продолжить незавершённую; invite link не выдаёт грант. Первая раздача после готовности трёх, только назначенный администратор создаёт комнату; проверить существующую ошибку допуска `Test` к create, не расширять права. Owner управляет назначением администраторов и архивированием; архив не удаляет результаты.

## 10. Магнитофон, музыка и звуки (PR13)

Оригинальный ретро-магнитофон с визуальными механическими кнопками, локальным изображением/вектором, увеличенный при общей команде. Не копировать товарные изображения с неясными правами. Размер достаточен для touch, закрытие любым игроком/клик по игровому полю. В увеличенном режиме: play/pause, предыдущая/следующая композиция, stop, отображение названия/позиции, личная громкость и mute; кнопки доступны мышью, клавиатурой и touch. Общая команда изменяет `track_id`, `playing`, `offset_at_change_ms`, `changed_at_server_ms`, `music_revision`; при воспроизведении `position=offset+(now_server−changed_at_server)` с проверкой duration/границ; при pause/stop позиция фиксирована. Пример: старт с 10 с, через 90 с вернувшийся получает 100 с. Примерная целевая синхронизация аудио между клиентами ≤ 1 с после готовности декодера и user gesture; измерять drift, корректировать плавно/редко. Не передавать аудио потоком через Render, не использовать файлы из личной подписки или неизвестных источников как серверное аудио. Музыка продолжает играть во время игровой паузы и отключения одного, пока нет общей команды pause/stop. Закрытие радио снимает только `shared_overlay`; музыка продолжает играть.

Браузер может блокировать autoplay: показать «Включить звук» и после разрешённого жеста догнать общую позицию; не считать отсутствие аудио отказом подключения. У каждого свой mute/volume; не давать участнику дистанционно увеличить громкость чужого устройства. Манифест разрешённых треков содержит ID, title, artist, duration, asset URI, основание прав/лицензию. До предоставления законного источника — пустой плейлист и рабочие кнопки на собственных/разрешённых тестовых звуках; известные коммерческие композиции из молодости не входят в поставку и не обещаются бесплатно. Медиа- и музыкальные ассеты не загружать на каждый heartbeat, использовать кэш, измерить трафик. При недоступности трека показать предупреждение, не останавливать игру. Сценарии: два игрока одновременно нажали next, reconnect во время pause, переключение трека, autoplay rejection, локальный mute, закрытие магнитофона без прекращения музыки.

## 11. WebRTC и длительная запись (PR13)

### 11.1. Связь

Mesh на 3 участников: два peer connections на игрока, камеры и микрофоны независимо, в отдельных зонах стола. Использовать существующую медиа-логику как основу, заменить регулярный Firestore signalling polling на адресные WS-события (через существующие роли и проверку membership). Если WS недоступен, контролируемый fallback или временное отключение медиа, не 2,5-секундный polling шесть часов. SDP/ICE только получателю, bounded queue, expiry, отсутствие приватного игрового состояния в медиа. Не логировать IP/SDP/ICE; никаких платных TURN, гарантировать соединение через каждый NAT нельзя. STUN — доступность и условия проверить. Переключение devices, повторное соединение, reconnect и audio mixing протестировать на реальных браузерах. Стабильный размер видеопанели; декодирование не должно ухудшать обработку хода; при нагрузке снижаем resolution/frame rate (проектный default 360p–480p, 15–24fps, настраиваемо), не закрываем игру. Не отправлять камеру/микрофон без user gesture. При отключении обоих человек всё равно игрок и имеет право решать вопрос записи общего стола.

### 11.2. Согласие и приватность записи

Любой из трёх может запросить запись, сам выражает согласие, оба соперника явно подтверждают; один сеанс на комнату, `record_id` и согласия связаны с конкретными тремя участниками. Индикатор/инициатор/кнопка отзыва всегда видимы (даже при overlay/portrait/перерыве). Запись общего стола + только разрешённые камеры/голос, никогда экран целиком или личные карты. Остановить локально на revoke, неизвестном/просроченном consent, offline/потере управляющего канала, скрытии вкладки при недоказанной безопасности, ошибке writer/recorder. Удалённый отзыв посылается немедленно по WS и локальный fail-closed watchdog ограничивает окно при потерянной связи (сохранить или усилить 8-секундное ограничение PR9; целевой результат на живом канале ≤ 500 мс после получения события). Технически невозможно гарантировать мгновенную остановку на чужом устройстве при OS/JS suspension или внешнем recorder; не выдавать за выполненное абсолютное требование. При возобновлении после disconnect использовать прежние согласия только если тот же контекст, все действительны и отсутствие отзыва подтверждено сервером, без новой молчаливой записи. При неизвестном состоянии — новый явный запрос. Разрыв может закончить текущий файл; не обещать бесшовный контейнер после остановки. Уже сохранённый отрезок не удаляется дистанционно. Никаких файлов/медиабайтов в Firestore, Render, Vercel, Storage; хранить только минимальные записи согласий/аудита с ограниченным доступом. Запись не обязательна для игры и отключена feature gate до безопасной приёмки.

### 11.3. Запись 4–6 часов

`canvas.captureStream` + Web Audio mix разрешённых источников + `MediaRecorder` с browser-supported MIME, последовательная запись `dataavailable` в File System Access writable stream (`showSaveFilePicker` с жестом и HTTPS, feature detection). При 1 Мбит/с × 21600/8 ≈ 2,7 GB; при 2 Мбит/с ≈ 5,4 GB (десятичные единицы, bitrate общий, фактический файл отличается). Не хранить весь набор `Blob[]` до stop. Ограничить очередь байтов/время writer backpressure; при превышении, нехватке диска, отказе доступа, закрытии вкладки или write failure — остановить и сохранить всё, что реально можно завершить, явно сообщить пользователю. В поддерживающих браузерах один файл для непрерывного сеанса; проверить совместимость контейнера с последовательной записью и финализацией. `timeslice` не точный таймер, события могут задерживаться. Fallback: ограниченные самостоятельные воспроизводимые сегменты (инженерный default 15–30 минут и меньший предел по байтам, определяемый замером), каждый корректно завершён новым MediaRecorder/контейнером, а не произвольный отдельный chunk WebM. Пользователь заранее узнаёт режим, выбирает каталог/сохраняет файлы с предсказуемыми номерами; запрет браузером последовательного сохранения — предупреждение и безопасная остановка, не рост RAM. Не объединять сегменты автоматически в облаке. Уточнить срок хранения служебных метаданных по PR9, ручная bounded cleanup без TTL billing. Legacy коллекции PR8 не удалять автоматически; migration/cleanup только Owner после проверки.

Источники: [MDN MediaRecorder](https://developer.mozilla.org/en-US/docs/Web/API/MediaRecorder), [dataavailable](https://developer.mozilla.org/en-US/docs/Web/API/MediaRecorder/dataavailable_event), [showSaveFilePicker](https://developer.mozilla.org/en-US/docs/Web/API/Window/showSaveFilePicker). Реальные совместимые браузеры и форматы фиксировать после испытания, не до него.

## 12. Безопасность, миграции, доступ и эксплуатация

- Существующая Firebase Auth и Portfolio Lab grants остаются основой. `No Access` — отказ; `View` — разрешённые read-only разделы; `Test` — игровые действия занятого места; `Admin`/назначенный game admin — создание/активные корректировки в пределах матрицы; `Owner` — управление grants/назначениями и архив. Роль проекта не означает право видеть закрытые руки. Модульные host adapters не импортируют чужие internals. Firestore browser rules deny-all для закрытых коллекций; никаких новых прямых клиентских Firestore listeners с private state.
- Проверять direct Render origin, BFF, handshake, все роли, expired/revoked grant, cross-room и повторный ticket, дубли вкладок, payload bounds, origin, XSS, логирование. Не вводить общую публичную комнату, никакой hardcoded uid, ключей, email, реальных фото друзей, приватных записей и seed с реальными данными. Ограниченные безопасные логи: stage/error class/request ID, без raw state, tokens, SDP, private cards. Сохранить HTTP 503 SDK fix и корректную транзакционную семантику реального Firestore.
- Данные: аддитивное versioned schema с default для legacy room без новых полей; lazy upgrade только атомарно и проверяемо, совместимость старого HTTP клиента пока rollout; существующая история и score неизменны. Не переписывать завершённые партии, не делать разрушительных миграций, не очищать production данные в CI. При несовместимости откатить флаги/код, не данные. До каждого PR проверить локальный `main` и состояние docs; не переносить прошлые синтетические файлы вместо актуальных.
