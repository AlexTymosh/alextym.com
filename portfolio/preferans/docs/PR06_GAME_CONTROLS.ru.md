# PR 6 — серверные счётчики, отмены и административные поправки

**Основание:** `FULL_TECHNICAL_SPECIFICATION.ru.md`, разделы 5.6, 15, 16, 22. Следуем этим правилам, а не случайным вариантам преферанса.

**Статус:** интеграционный пакет для PR 6. Код не включается в production автоматически. Все операции зависят от действующего `PREFERANS_ROOMS_ENABLED` и текущего гранта Portfolio Lab, сохраняются транзакционно в серверной Firestore-коллекции `preferans_rooms`; клиентские Firestore Rules по-прежнему запрещают прямое чтение и запись.

## 1. Элементы

| Действие | Кто вправе | Условия |
|---|---|---|
| `POST .../commands`, `action=pulse` | Только игрок своего места | Авторизованный heartbeat, для обнаружения потери связи |
| `action=counter_start` | Любой соперник принимающего решение | Действующая сдача, нет другого счётчика, присутствуют все участники |
| `action=undo_request` | Автор последней отменяемой ставки/карты | После неё ещё не было другого игрового действия; причина обязательна |
| `action=undo_vote` | Каждый из двух других участников | 120 секунд по умолчанию, одно голосование на игрока; отказ/тайм-аут → нет отмены |
| `action=preset` | Администратор комнаты | Только **до первой раздачи**; изменяются числовые периоды и множитель |
| `POST .../adjust` | Администратор комнаты или глобальный Owner | Только незавершённая партия, причина и допустимые целочисленные поправки |

Все команды подписываются серверной Firebase-сессией через существующий Next.js BFF, имеют `expected_version` и `idempotency_key`; прямой доступ к Render проверяет те же права. `Owner` без занятого места может исправить публичный расчёт, но не получить чужие скрытые карты. `View` не отправляет команды.

## 2. Голосование и секретность

- На сервере в `private/current.controls.candidate` сохраняется сериализованный снимок **до** последней ставки или карты. Он никогда не попадает в `/view`, `/events`, публичный документ комнаты, HTML или JS state.
- Отмена карты допускается лишь до следующей карты и пока взятка не закончена. Отмена ставки — пока после неё не произошло другое торговое действие; повторные heartbeat/служебные операции не лишают права запросить отмену.
- Два игрока голосуют отдельно; одно «нет» достаточно. При двух «да» прежнее состояние восстанавливается в одной Firestore-транзакции, а принятое действие и решение об отмене **остаются** в append-only журнале событий.
- Пока голосуют, обычные игровые команды блокируются, а время на счётчике сохраняется. Идентифицируются только места 0/1/2, без списков UID.

## 3. Счётчик и пауза

- По умолчанию срок 180 секунд, штраф `3 × C_ref` в гору задержавшегося участника, повторение каждые полные 180 секунд; стоимость `C_ref` фиксируется в начале каждого счётчика. До первой заявки используется стоимость минимальной разрешённой игры; для мизера — 10.
- **Распасы:** `C_ref = 1/2/3` на соответствующей ступени. Это открытое инженерное допущение исходного ТЗ, **не** подтверждённое историческое правило.
- Полная цена и SHA256 набора правил фиксируются в приватном состоянии счётчика; истёкшие периоды записываются в ScoreState как числовая горá с отдельным `LedgerEntry` и в серверный append-only журнал.
- Нет process-timer: при новом запросе server timestamp используется для атомарного пересчёта пропущенных периодов, в том числе после сна Render. **До следующего запроса UI/Firestore могут ещё не показывать нового штрафа.**
- По умолчанию клиент сообщает о присутствии каждые 45 секунд. Если присутствие любого игрока старше 100 секунд, при следующем запросе система приостанавливает счётчик/голосование, сохраняет оставшееся время; возобновляет после сигналов всех троих.
- Ограничение HTTP-эвристики: это не мгновенное обнаружение потери соединения. В узком промежутке до признания отсутствия игрока срок может быть зачтён — для точного гарантированного немедленного offline pause нужен отдельный transport/presence review до выпуска. Не выдавать этот прототип за полностью проверенный безупречный таймер.

## 4. Административные корректировки

- Поля: `hill`, `pool`, направленный `vist`. Только целые delta ±1..1000 и причина 5–180 символов. Отрицательная горá и висты, недопустимая пуля, висты на самого себя и закрытие всех пуль посредством ручной корректировки запрещены.
- Предпросмотр before→after на клиенте не считается доказательством: сервер независимо проверяет в текущей версии и атомарно возвращает новое immutable `ScoreState`.
- **Исходные автоматические `LedgerEntry` сохраняются**. Корректировки имеют отдельные append-only room events (`before`, `delta`, `after`, `reason`, `created_at_ms`, `game_version`, `deal_id`, место администратора). В приватном документе держатся только последние 20 для быстрого отображения; полная история — `/events` с серверной проверкой доступа.
- Для исправления прежней корректировки создаётся компенсирующая новая операция. После статуса `closed` — 409 для всех, включая Owner.
- Это не даёт возможность менять торговлю, сыгранные карты или завершённые партии.

## 5. Числовые параметры

Перед первой раздачей администратор может настроить: `counter_seconds=60..600` (по умолчанию 180), `counter_multiplier=1..6` (по умолчанию 3), `undo_seconds=30..300` (по умолчанию 120). Это отдельный версионируемый room-control policy, а не изменение уже зафиксированного SHA256 схемы финансового `Ruleset`. После начала первой раздачи — запрет.

## 6. Что ещё не проверено и не входит в PR 6

- Настоящие Firebase Auth/Firestore Emulator **конфликтные** транзакции при трёх клиентах, восстановление после реального рестарта, точность определения offline на мобильных сетях.
- 100% немедленная пауза при отключении пользователя (HTTP polling в принципе не даёт такой гарантии).
- Полный редактор всех параметров исторического `Ruleset`, а также ручная коррекция отдельного старого `LedgerEntry` с ссылкой на `trick_id` / `ledger_entry_id` (текущая поправка привязана к сдаче и версии).
- Голосование о случайно показанной закрытой карте, доказательство оставшихся взяток на мизере, административное архивирование, pause SLA, комплексная балансировка бесплатных Firestore reads/writes и ограничение объёма журнала heartbeat.
- Полный реальный Playwright E2E с тремя независимыми Firebase сессиями; текущие тесты — тесты контракта и локальный FakeDB.

**Перед production:** дополнительно проверить Firestore quotas. При трёх игроках постоянный polling и heartbeat создают существенные чтения, операции и события, которые могут превысить бесплатный лимит при долгой непрерывной игре. Измерить на emulator/monitoring, не подключать платный план автоматически.
